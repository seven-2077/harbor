## 抽样口径（必须按此理解派生文件）

1. **时间窗**：2026-08-03 00:00:00 至 2026-08-09 23:00:00（含），即 2026-08-03（周一）至 2026-08-09（周日）完整一周。日期为 parquet 中的 `transit_timestamp`（纽约当地时间，无时区后缀）。完整 8 月文件覆盖 2026-08-01 至 2026-08-31，31 天无缺失日。
2. **空间/系统**：周汇总与点图层只保留 `transit_mode = subway`，不含 Staten Island Railway 与 Roosevelt Island Tram。8 月整月 parquet 仍含这二者（SIR 6,732 行，tram 5,923 行）。
3. **汇总规则**（仅针对周汇总 CSV）：同一 `transit_timestamp + station_complex_id` 下，对各 `fare_class_category` 的 `ridership`、`transfers` 求和；`n_fare_class_rows` 记录被合并的票种行数。`transfers` 仍是 `ridership` 的子集，求和后也不可再加到 ridership 上。
4. **未抽样的官方全量**：Beginning 2025 官方表在 2026-11-11 读到的元数据为 47,409,293 行，时间至 2026-10-29。全量未下载（体积大，且本机 curl 被 data.ny.gov 拒绝）。

## 字段与来源

### A. `gtfs_subway.zip`（官方）

解压后 10 个文本表。本机打开后的行数（不含表头）与字段：

- `agency.txt` 1 行：agency_id, agency_name, agency_url, agency_timezone, agency_lang, agency_phone。实测 `agency_timezone=America/New_York`。
- `feed_info.txt` 1 行：日历 **2026-11-01 至 2027-05-15**，版本 `20261028-fall-2026-pick-with-long-term-supplements`。
- `calendar.txt` 3 行（Sunday / Saturday / Weekday）；`calendar_dates.txt` 10 行。
- `routes.txt` 29 行：route_id, agency_id, route_short_name, route_long_name, route_desc, route_type, route_url, route_color, route_text_color, route_sort_order。route_type 计数：1 有 28 条，2 有 1 条（SIR）。短名包括 A,C,E,B,D,F,FX,M,G,J,Z,L,N,Q,R,W,S（3 条），1–7、6X、7X、SIR。
- `stops.txt` 1,488 行：stop_id, stop_name, stop_lat, stop_lon, location_type, parent_station。其中 `location_type=1` 的父站 496 个，其余 992 行为带 N/S 方向的站台。
- `trips.txt` 20,310 行：route_id, trip_id, service_id, trip_headsign, direction_id, shape_id。按 service_id：Weekday 8,498，Saturday 6,186，Sunday 5,626。唯一 shape_id 261 个。
- `stop_times.txt` 562,943 行：trip_id, stop_id, arrival_time, departure_time, stop_sequence（本包无 pickup_type 等扩展列）。
- `shapes.txt` 153,567 行：shape_id, shape_pt_sequence, shape_pt_lat, shape_pt_lon。
- `transfers.txt` 613 行：from_stop_id, to_stop_id, transfer_type, min_transfer_time。

**与客流样本的日历关系（事实）**：这份官方 Regular GTFS 的服务日历从 2026-11-01 起，而客流样本是 2026-08。二者**没有重叠日期**。车站与线路空间层仍可用于底图（车站位置相对稳定，但这是推断，不是实测“8 月与 11 月网络完全相同”）。若要把 `stop_times` 当作 8 月实际时刻表去和客流比对照，需要另下与 2026-08 重叠的历史 GTFS；Transitland 目录里有候选归档，但今晚其 API 无密钥返回 401，**未下载**。

### B. 小时客流（官方字段 + 本月样品）

官方 12 列见 `来源与许可证/客流数据字典与第三方说明摘录.md`。transitlab 的 8 月 parquet **没有** `georeference`，其余 11 列名称与官方一致；`ridership`/`transfers` 为整数，`transit_timestamp` 为时间戳。

8 月 parquet 实测：1,706,182 行；subway 1,693,527 行、SIR 6,732、tram 5,923；唯一车站复合体 428 个（含非 subway）；subway 进站人次合计 105,456,157（对该月 `ridership` 求和）。无空值。

周汇总 CSV 字段：`transit_timestamp, station_complex_id, station_complex, borough, latitude, longitude, ridership, transfers, n_fare_class_rows`。该周 subway 进站人次合计 24,833,349，transfers 合计 1,339,883，唯一复合体 424 个。

### C. 官方车站对照（未落全表文件）

官方数据集 “MTA Subway Stations”（`39hk-dx4f`）有 496 行，关键字段：`gtfs_stop_id`、`station_id`、`complex_id`、`stop_name`、`daytime_routes`、`gtfs_latitude`、`gtfs_longitude` 等。

连接方式（已用三份材料交叉核对例子，不是臆造键名）：

- 客流 `station_complex_id` = 车站表 `complex_id`（注意类型：客流里是文本，车站表元数据里是数字）。
- 车站表 `gtfs_stop_id` = GTFS `stops.stop_id`（对应 `location_type=1` 的父站）。
- 一个 `complex_id` 可对应多个 GTFS 父站。已核例子：Prince St 客流 id `17` ↔ 车站表 complex_id 17、gtfs `R22`；Hewes St 客流 id `100` ↔ gtfs `M14`；Times Square 客流 id `611` 在车站表中有多行（含 `R16`、`A27`、`127`、`725`、`902` 等）。

请用 `download_samples.sh` 或官方 SODA URL 自行保存全表。本机今晚对该域 curl 为 403。

## 使用注意（给 Helix / Lumen）

- 周汇总 CSV 可直接用 Excel、pandas、QGIS 打开（约 5.5 MB）。整月 parquet 需 pyarrow、fastparquet 或 DuckDB。
- 客流是**进站人次估计**，不是完整 OD 出行；同一小时同一车站必须把各票种相加才是总进站。
- 不要把 `transfers` 再加进 `ridership`。
- 不要把当前 GTFS 的 `stop_times` 当成 2026-08 的运营时刻表。
- 地图底图请自备（OSM 等），不要未经许可使用 MTA 官方地图或标志。
- 成品中应注明数据来自 Metropolitan Transportation Authority；客流若用了 transitlab 月文件，请同时写明“MTA 数据，经 data.ny.gov 发布，本样本取自 transitlab.nyc 的 2026-08 月度文件”。

### 公开对照数据的口径

1. 请求坐标 (36.06, 103.83) 是兰州市区**参考点**，不是实测校园或实验室坐标。空气质量与气象被吸附到**不同**格点，对照时必须分别使用各文件元数据里的经纬度。
2. 时间窗 2026-08-03 至 2026-08-09 与选题 A 的纽约客流样品周相同，只为方法演示方便。两城不能做空间对照。
3. 许可证为 CC BY 4.0，另须按 `来源与许可证/Open-Meteo_许可证与条款摘录.md` 写明 Open-Meteo 与 CAMS / Copernicus 归属。托管免费 API 另有非商业与速率限制。
4. 空气质量文档称数据基于 CAMS 欧洲约 11 km 与全球约 45 km 产品；兰州不在欧洲域，且本样品 CSV 未给出 domain 字段，故不把网格间距写成已核实值。

### 模拟 STM32 流的口径

1. 文件头已标明「模拟，非实机」。数值为发明，仅 loosely 参考同日 12:00 兰州室外公开气象量级（温度 25.8 °C、相对湿度 49%、地面气压 852.4 hPa），再加室内偏差与噪声。
2. 字段：`timestamp_utc, timestamp_local, device_id, firmware_rev, seq, sensor_id, bus, channel, raw_value, value, unit, quality_flag, source, notes`。`device_id` 占位符为 `stm32-f4zg-sim-01`。
3. 通道（均为推断的常见配置，不是已核实 BOM）：BME280 的温度 / 湿度 / 气压，BH1750 照度，MQ135 的 ADC 原始码与未标定指数，以及片内温度 `MCU_TS`（`quality_flag=relative_only_simulated`）。
4. Helix 应用同一解析器读 CSV 或 JSONL（跳过 `#` 行），再视需要解析 USART 示例。不得把这些行当作实机采集。
